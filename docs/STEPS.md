# Steps

1. Money first (`money.py`): integer minor units, per-currency exponents, `Decimal` rates from a static file, and `allocate()` (largest remainder, deterministic tie-breaks). Property-tested before anything else existed.
2. Simplification (`simplify.py`): net balances, a heap-based greedy min-cash-flow, then an exact bitmask search for small groups. Tested against a brute-force oracle.
3. Schema: integer `CHECK`s on every amount, `CHECK (from_user <> to_user)`, foreign keys with cascades, and append-only triggers on `activity`.
4. Services: one function per business rule, taking an open transaction. Authorization lives here (`require_member`), not scattered across routes.
5. Idempotency: `run_idempotent()` stores the key and response in the same transaction as the write.
6. HTTP layer: pydantic with `extra="forbid"` and `StrictInt` (no floats or bools as money), argon2 auth, httpOnly SameSite cookie, Origin check on writes, CSP with no inline script, rate limits on auth and join.
7. Client: vanilla JS, `textContent` only, string-and-integer money parsing, an inline-SVG balance chart, an idempotency key per submit (kept across retries, reset on any edit).
8. CSV export with formula-injection defence, and a seed script that uses the same service functions as the API.
9. Tests: 53, including the IDOR suite. Then I broke the authorization on purpose three ways to confirm the suite notices.

# Interview Q&A

**1. Why store money as integers, and what are the traps?**
Binary floating point can't represent most decimal fractions (`0.1 + 0.2 != 0.3`), and errors accumulate across thousands of additions, so ledgers stop balancing. Integer minor units (cents, paise) make addition exact and equality meaningful, and a database `CHECK (amount_minor > 0)` can enforce sanity. The traps: currencies differ in exponent (JPY has none, KWD has three) so "×100" is wrong; JSON numbers are floats in many clients, so I use strict integer parsing server-side (`12.5`, `"12"` and `true` are rejected) and parse typed amounts in the browser with a regex rather than `parseFloat`; and integers only help if you also keep conversion and division exact. Exchange rates are parsed straight to `Decimal`. JavaScript numbers are exact up to 2^53, and I cap amounts at 10^12 minor units, so client-side display maths stays exact.

**2. How do you handle rounding, and who gets the odd cent?**
Two separate roundings. Currency conversion happens once, when the expense is created: `Decimal` arithmetic, rounded half up to a whole minor unit (the usual convention for money; banker's rounding would be the alternative to avoid systematic bias). The result and the rate are stored, so changing the rates file later can't rewrite history. Splitting uses the largest remainder method on integers: everyone gets `floor(total × weight / sum)`, and the leftover units (always fewer than the number of people) go to the largest fractional remainders. The parts sum to exactly the total, and each is within one unit of the exact proportion. Ties are broken by position rotated by a per-group expense counter, so with 100.00 split three ways the extra cent moves around instead of always landing on the same person (a test checks that over 300 expenses each person gets exactly 100 extra cents). It's deterministic: sorted by user id, no randomness, so the same request always produces the same shares regardless of the order the client listed people in.

**3. How does debt simplification work, and what's its complexity?**
Net each person's position (paid minus owed, adjusted for settlements). Positives are creditors, negatives debtors. The greedy min-cash-flow repeatedly matches the biggest creditor with the biggest debtor and transfers the smaller of the two amounts; that zeroes at least one person each step, so it needs at most `n-1` payments, and with heaps it runs in O(n log n). But greedy isn't always minimal. The true minimum is `n` minus the maximum number of disjoint zero-sum groups, and finding that is NP-hard (it generalises the partition / subset-sum problem). Example: balances +7, +5, -4, -3, -5 contain two independent groups ({7,-4,-3} and {5,-5}) and need 3 payments; greedy uses 4. So for up to 14 people I solve it exactly with a bitmask DP over subsets, O(2^n · n) time and O(2^n) memory, then run greedy inside each zero-sum group. Beyond 14 it falls back to greedy. I checked the exact path against a brute-force oracle on 250 random small groups. One product caveat: simplified payments can pair people who never transacted with each other, which is correct for settling but surprising to read.

**4. What is IDOR and how is it prevented here?**
Insecure direct object reference: the server trusts an id from the client (`/groups/7/expenses/42`) without checking the caller may access that object. Here, ids are plain sequential integers, so a user can try every number. Defences: every group-scoped route calls `require_member` first; child objects are fetched with their parent (`e.id = ? AND e.group_id = ?`), so being a member of group 8 doesn't let you reach expense 42 of group 7 through `/groups/8/...`; ids referenced inside a body (payer, split participants, settlement parties) must belong to the group, otherwise someone could write another user's id into their own group; and non-members get the same 404 as for a nonexistent id, so you can't even confirm something exists. Tests cover every route as an outsider, id enumeration (ids 1 to 59 reach only your own group), cross-group expense ids, forged participants, replaying another user's idempotency key, and a logged-out token. I also mutation-tested it: removing a membership check, un-scoping the expense lookup, and ignoring the user in `require_member` each made specific tests fail. Gaps: no per-user rate limit on reads, and authorization is only as good as remembering to call the helper in each new route (a route-level dependency or row-level security would make forgetting harder).

**5. How do idempotent writes work, and what can still go wrong?**
Networks drop responses, so clients retry, and a retried "add expense" must not charge twice. The client sends an `Idempotency-Key`. Server-side, in one `BEGIN IMMEDIATE` transaction: look up `(user, key)`. If a row exists with the same request hash, return the stored response and don't write; if the hash differs it's a client bug, so 422; otherwise do the write and store the key and response in that same transaction, so a crash can't leave the data without the key or the key without the data. `BEGIN IMMEDIATE` takes the write lock first, so two concurrent retries can't both pass the check (a test fires 10 threads at one key and gets exactly one write and nine replays). Failed requests roll back, including the key, so a corrected retry with the same key works. Keys are scoped per user, and group membership is checked before any replay, so keys can't be used to read another person's stored response. The client keeps one key per submit attempt and resets it on any edit. Limits: keys never expire (needs a TTL job), the hash covers the body but a different replay of the same key in another group is rejected only because the scope is part of the hash, and `DELETE` repeats return 404 rather than 204, which is idempotent in effect but not in response. Joining a group is naturally idempotent via `INSERT OR IGNORE`.

**6. How does the audit trail work, and how trustworthy is it?**
Every change writes an `activity` row (actor, action, entity, JSON detail, timestamp) in the same transaction as the change, so there's never a change without a log entry or a log entry for a change that rolled back. SQLite triggers abort any UPDATE or DELETE on that table, and expenses are soft-deleted with `deleted_by` and `deleted_at`, keeping their splits, so the history of "who deleted what" survives. Expense rows also keep the original amount, currency and the rate used. What it isn't: tamper-proof. Anyone with write access to the database file can drop the triggers. A stronger design would chain each entry's hash to the previous one (tamper-evident), or ship entries to a separate write-only store. It also doesn't log logins or failed authorization attempts, which a real system would want for security auditing.
